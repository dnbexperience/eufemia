## Auto-level bugs

Each example below corresponds to exactly one row of the findings tables. The
`debug` prefix (`[hN]`) shows the level that is **actually** rendered; the
heading text is the **expected** level, and a trailing `X` marks a mismatch.

**NB:** Examples without a `reset` boundary (A3, C1, C-ref, E1, G6) depend on
the surrounding page state, so on this live page their `[hN]` prefix may differ
from the isolated value — that context-dependence is itself part of the findings.

## Context, reset & skipCorrection interactions

Unlike the groups above, these demos label each heading with its **actual**
rendered level (so the `[hN]` prefix matches) — they document _rules_, not
bug-vs-expected. Read each description for what is surprising. All are isolated
with a `reset` so they stay deterministic on this page.

### Group H1 — heading ↔ context

#### H1 — a plain heading after a context resumes the _pre-context_ level

The `d` after the nested context is **h2** (the level before the context), not h3 (the context's last heading). Plain `Heading.Level` is isolated for following siblings.

<HeadingRowH1 />

#### H2 — an `inherit` heading after a context jumps to the _last-inside_ level

The `inherit` heading is **h3** (the context's last heading), not h2. `inherit` crosses the boundary a plain heading respects.

<HeadingRowH2 />

#### H3 — a plain heading after a `skipCorrection` context → pre-context

The context's internal `h5` does **not** leak; the following plain heading is **h2**.

<HeadingRowH3 />

#### H4 — an `inherit` heading after a `skipCorrection` context → inside-last

Same setup as H3 but with `inherit`: the following heading becomes **h5**.

<HeadingRowH4 />

#### H5 — a heading before a context sets the context's baseline

The context's first child inherits the preceding heading's level (**h2**).

<HeadingRowH5 />

### Group H2 — Increase/Decrease isolation & chaining

#### H6 — a plain heading after `Heading.Increase` cannot return to h1

Pre-context was h1, but the following sibling is bumped to **h2** (the "no second `<h1>`" rule leaking across the boundary).

<HeadingRowH6 />

#### H7 — sibling `Heading.Increase` contexts chain

Two sibling increases accumulate (**h2** then **h3**) rather than each starting from the parent level.

<HeadingRowH7 />

#### H8 — `Heading.Level` + an `increase` child double-counts

`[h1, Level{ increase }]` → **h3**, skipping h2 — whereas `Heading.Increase` in the same spot yields h2 (see H6). Same "increment once" intent, different result.

<HeadingRowH8 />

### Group H3 — nesting: accumulate & boundary

#### H9 — nested `Increase` accumulates

h1 → h2 → **h3**, one level per nesting.

<HeadingRowH9 />

#### H10 — nested `Increase` is swallowed at the h6 cap

From h5, two nested increases give **h6, h6** — the second is lost at the ceiling.

<HeadingRowH10 />

#### H11 — nested `Decrease` accumulates from a high start

From h6, two nested decreases give **h5, h4** (not stuck) — decrease accumulates like increase.

<HeadingRowH11 />

#### H12 — nested `Decrease` is swallowed at the h2 floor

From h3, two nested decreases give **h2, h2** — the second hits the "no second `<h1>`" floor.

<HeadingRowH12 />

#### H13 — nested `Heading.Level inherit` does NOT accumulate

Both levels stay **h2** — `inherit` on a plain Level just reuses the level.

<HeadingRowH13 />

#### H14 — nested `Heading.Increase inherit` DOES accumulate

h3 → **h4** per nesting — Increase still increments even with `inherit`.

<HeadingRowH14 />

### Group H4 — two contexts in sequence

#### H15 — a plain second context resumes the pre-context level

The second context's heading is **h2**, like a plain heading after (H1).

<HeadingRowH15 />

#### H16 — an `inherit` second context jumps to the first context's last-inside

The second context's heading is **h4**, like an `inherit` heading after (H2).

<HeadingRowH16 />

#### H17 — inside usage changes what `inherit` picks up

When only the _last_ inside heading uses `level`, the earlier auto heading keeps the baseline low, so `level={4}` clamps to **h3** and the following `inherit` picks up **h3** (vs h4 when all inside headings use `level` — H16).

<HeadingRowH17 />

### Group H5 — reset

#### H18 — a nested `reset` overrides the parent (down)

`reset=2` inside `reset=3` → **h2**; the heading after the inner context resumes **h3**.

<HeadingRowH18 />

#### H19 — a nested `reset` overrides the parent (up)

`reset=3` inside `reset=2` → **h3**.

<HeadingRowH19 />

#### H20 — `reset=1` injects an `<h1>` mid-document

`reset=1` inside `reset=3` forces **h1** right after an h3 — a non-monotonic outline (h3 → h1 → h3).

<HeadingRowH20 />

#### H21 — a reset value does not leak forward, but the h1-bump applies

After the `reset=3` context, the next sibling is **h2** (not the pre-context h1, and not h3) — the reset value does not leak, but a sibling after an h1 still can't be h1.

<HeadingRowH21 />

#### H22 — `reset` bypasses the factor-one rule

`reset=4` after an h2 jumps straight to **h4** (skipping h3); the heading after resumes **h2**.

<HeadingRowH22 />

### Group H6 — skipCorrection

#### H23 — `skipCorrection` + `level` is honored absolutely

`skipCorrection level={6}` after an h4 renders **h6**, bypassing the factor-one clamp (a normal heading would become h5).

<HeadingRowH23 />

> **Not shown (render crash):** a `skipCorrection` heading or context with **no** `level` (and no `inherit`/`increase`) leaves the level at `0`, so `getHeadingElement(0)` returns `undefined` and React throws `"Element type is invalid"`. It is omitted here because it would crash the page.
